# **Домашнее задание**
### Оркестрация моделей в Triton Inference Server

**Цель:**
В этом ДЗ вам предстоит развернуть сложный ML-пайплайн в NVIDIA Triton и провести его нагрузочное тестирование. Вы научитесь конфигурировать разные бэкенды для моделей и настраивать бизнес-логику на уровне сервера.


**Описание/Пошаговая инструкция выполнения домашнего задания:**

1. **Подготовка моделей и структуры репозитория.**  
 - Подготовьте три разнородные легковесные модели для демонстрации работы разных бэкендов:  
   1. Модель классификации: Например, крошечный BERT или классификатор на базе Scikit-learn (в формате ONNX).  
   2. Модель эмбеддингов: Например, Sentence-Transformer (в формате ONNX или через Python-бэкенд).  
   3. Модель генерации: Малая LLM (например, Qwen-0.5B или TinyLlama), оптимизированная через vLLM или TensorRT-LLM.  

 - Спроектируйте и создайте файловую структуру Model Repository строго по стандартам Triton:  
   1. Создайте папки для каждой модели с версионированием (папка 1/).  
   2. Подготовьте файлы конфигурации config.pbtxt для каждой модели.  
   3. Опишите в конфигах входные (input) и выходные (output) тензоры, их типы данных и размерности.  
   4. Выберите и настройте бэкенды для каждой модели (например, onnxruntime для классификации и vllm для генерации).  

2. **Разработка бизнес-логики (Business Logic Scripting — BLS).**
 - Создайте отдельную «ансамблевую» модель (на базе Python Backend), которая будет выступать дирижером всей системы.

 - Напишите Python-скрипт (model.py), реализующий логику BLS:  
   1. Прием входного запроса от пользователя.  
   2. Последовательный или параллельный вызов других моделей внутри Triton (используя pb_utils.InferenceRequest).
   3. Логика обработки: например, сначала получаем эмбеддинг текста - на основе эмбеддинга вызываем классификатор - если класс «вопрос», отправляем текст в модель генерации.
   4. Сборка финального ответа и возвращение его клиенту.
   5. Настройте config.pbtxt для этой BLS-модели, указав зависимости от других моделей.  

3. **Развертывание в Docker и запуск сервера.**  
 - Подготовьте Dockerfile или используйте готовый образ nvcr.io/nvidia/tritonserver.  
 - Настройте запуск контейнера с пробросом нужных портов (8000 для HTTP, 8001 для gRPC, 8002 для метрик) и монтированием папки model_repository.  
 - Запустите сервер и убедитесь через логи (tritonserver --model-repository=/models), что все модели успешно перешли в статус READY.  
 - Напишите простой клиентский скрипт на Python (используя tritonclient), чтобы проверить работоспособность всей цепочки (BLS-пайплайна) через один запрос.  

4. **Нагрузочное тестирование и анализ слабых мест.**  
 - Используйте утилиту Perf Analyzer (часть Triton SDK) для проведения нагрузочного тестирования.  
 - Выполните замеры для двух сценариев:  
   1. Нагрузка на каждую модель по отдельности.
   2. Нагрузка на всю цепочку через BLS-модель.

 - Проанализируйте полученные метрики:  

   1. Throughput (Пропускная способность): Сколько запросов в секунду (RPS) выдерживает система.  
   2. Latency (Задержка): Какое время занимает выполнение запроса на разных этапах (Queue, Compute Input, Compute Infer, Compute Output).  

5. **Отчёт и анализ.**  
 - Соберите результаты в GitHub-репозиторий. Опишите, что настроено, и приведите следующие артефакты:  

   1. Иерархическое дерево вашего Model Repository.
   2. Содержимое файлов config.pbtxt и код вашего BLS-скрипта (model.py).
   3. Отчёт о тестировании: Скриншоты или текстовые логи работы Perf Analyzer с итоговыми цифрами Latency и Throughput.
   4. Графики или таблицы со сравнением производительности моделей.
   5. Сделайте вывод: какие преимущества дает использование Triton и BLS по сравнению с обычным Flask/FastAPI сервисом? Предложите способы оптимизации (например, включение Dynamic Batching или Instance Groups), если задержки оказались слишком высокими.
